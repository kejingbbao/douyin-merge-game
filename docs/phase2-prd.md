## 1. 项目信息

- **Language**：中文
- **Programming Language**：纯 Canvas 渲染 + 原生 `tt.*` API，零 npm 依赖（**不使用** Vite+React+MUI 默认栈，因项目基线约束为零依赖小游戏）。后端复用 Vercel serverless + Upstash Redis（新加坡节点，同一实例）。
- **Project Name**：`phase2_real_time_room_battle`
- **原始需求复述**：在已上线的异步天梯（Phase 1）基础上，新增「实时房间对战」——2 人凭 6 位房码同房、同 seed 开局、1.5s 轮询实时同步比分、局终按「先到 2048 胜 / 180s 到点比分高者胜（平分平局）」判定胜负；断线可在 TTL 600s 内重连。复用同一 Upstash 与 Vercel 项目，零新平台。

---

## 2. 产品目标

让两位玩家通过 6 位房码进入同一房间、**同房同种子同步开局**，在对局中实时看到对手的分数与步数进度，并由服务端权威判定「先合成 2048 者胜 / 180s 到点比分高者胜（平分平局）」，结束后可一键再来一局——整套链路在 2 人小房间内实现轻量、可重连的实时对战体验。

---

## 3. 用户故事

1. **As a 房主**，I want 创建房间后立即获得一个 6 位房码并能分享给朋友，so that 朋友凭码即可加入同房对战，无需全局匹配大厅。
2. **As a 加入者**，I want 凭房码加入后双方用同一个随机种子开局，so that 两人起始棋盘完全一致、对局起点公平。
3. **As a 对局中玩家**，I want 在 HUD 上实时看到对手的分数和步数（约 1.5s 刷新一次），so that 我能感知对手进度、调整自己的节奏。
4. **As a 局终玩家**，I want 看到明确的胜负（或平局）结果卡，并能一键「再来一局 / 返回」，so that 对战有清晰收尾且可快速续玩。
5. **As a 断线玩家**，I want 在房间 TTL（600s）内凭房码重连即恢复当前对局状态，so that 短暂网络抖动不会让我直接判负出局。

## 4. 需求池（P0 / P1 / P2）

### P0（必须，MVP）

| 编号 | 需求 | 说明 |
|------|------|------|
| P0-1 | 创建房间获房码 | `POST /api/room/create` → 返回 6 位 `code` + `seed` + `status=waiting` |
| P0-2 | 凭房码加入 | `POST /api/room/join` → 第 2 人加入后 `status=playing` 并写 `startAt` |
| P0-3 | 同房同 seed 同步开局 | 客户端本地时钟 ≥ `startAt` 才 `initGame(makeRng(seed))`；3s 缓冲吸收轮询抖动 |
| P0-4 | 实时比分轮询同步 | 对战期每 1.5s `GET /api/room/state` 同步双方 `score` + `steps` |
| P0-5 | 落子进度上报 | 落子时 `POST /api/room/progress`（节流每步或 ≥500ms）上报 `score/steps/boardSummary` |
| P0-6 | 局终胜负判定 | 服务端 `computeMatch`：先到 2048 即胜；或 180s 到点比分高者胜，平分 `matchResult=3` |
| P0-7 | 结束展示结果 + 再来一局 | 全屏结算卡（胜负/平局 + 再来一局 + 返回），复用现有返回键双形态兼容 |
| P0-8 | 断线 TTL 600s 内重连 | `code+uid` 重连识别已存在玩家、不重复加人、返回现有 `seed/startAt/status` 恢复 |

### P1（体验增强，本期应做）

| 编号 | 需求 | 说明 |
|------|------|------|
| P1-1 | 房间内「等待对手」状态提示 | `waiting` 期的视觉/文案提示，房主轮询降频至 1s |
| P1-2 | 同步缓冲 3s 倒计时 | 第 2 人加入后展示 3s 开局倒计时，双方近似同步 |
| P1-3 | 轮询失败指数退避与 UI 提示 | 失败 1.5→3→4.5→上限 6s 退避；UI 显示「同步中…」但不卡死本地棋盘 |
| P1-4 | 天梯与房间入口共存 | 主菜单同时保留天梯入口与房间入口（均置于左上避系统胶囊） |

### P2（可延后，本期不做）

| 编号 | 需求 |
|------|------|
| P2-1 | 观战 |
| P2-2 | 房间内聊天 |
| P2-3 | 全局匹配大厅（替代房码） |
| P2-4 | 断线超 TTL 的续局 |
| P2-5 | 多房间（>2 人） |

## 6. 待确认问题（实现时需工程师 / 架构师留意）

> 下列为**仍存歧义或边界**点；已锁定的推荐默认值（2 人房 / 胜负规则 / 轮询 1.5s / TTL 600s / 缓冲 3s）不在此列。

1. **双满格不同步到达的胜负判定**：若双方棋盘均满格（无合法 move）但不同步到达，且无人先到 2048——此时是否按「对方满格即视为其提交终局」处理？还是以 180s 到点比分判定？需明确「满格即终局」是否作为隐性提交触发 `submitResult`。
2. **180s 到点瞬间双方分数相等的展示**：平局 `matchResult=3` 的结算卡文案已定为「平局」；但需确认「到点瞬间」的边界（是否含 `startAt+180000` 当帧内的最后一手分数）如何快照，避免临界点分数抖动导致误判。
3. **房主离开后房间归属**：`waiting` 期房主退出、`playing` 期房主断线超 TTL——房间是否自动转移给另一人（升为房主）或整体解散？当前方案未定义房主角色权限，仅约定「第 2 人触发 playing」，需补「房主缺失」的降级规则。
4. **progress 上报节流与 seed 漂移边界**：P0-5 节流「每步或 ≥500ms」，但若玩家在 500ms 内连落多步，需确认 `boardSummary` 上报的是「每步末态」还是「节流窗末态」，以免影响对手缩略进度的真实感（不影响 seed 一致性，仅展示层）。
5. **再来一局的新房码策略**：「再来一局」是复用原 `code/seed`（重开同一房间）还是新 `create`（换新码新 seed）？影响房主归属与分享链路，需明确。
6. **轮询窗口内对手退出（未到 TTL）的感知**：对手在 TTL 内主动退出（非断线）时，我方轮询 `state` 应返回何种 `status`/提示（如「对手已离开」），以及是否触发提前结算或等待——当前 `matchResult` 仅覆盖「到点/双方提交」，需补「单方退出」分支。
7. **`boardSummary` 在 HUD 的用途边界**：4.1 结构中 `boardSummary` 同时用于「进度展示」与「结算展示」，需确认 HUD 缩略进度是只显分数/步数（P0-4 仅要求 score+steps）还是也渲染缩略棋盘；若渲染缩略棋盘，其解码展示规范需单独定义。

## 7. 验收标准（P0）

以下为可测试验收清单，须全部通过方可视为 P0 完成：

- [ ] **AC-1 建房获码**：调 `create` 返回 6 位 `code` + 非零 `seed` + `status=waiting`。
- [ ] **AC-2 凭码加入**：第 2 人 `join` 后 `status` 变为 `playing` 且 `startAt` 已写入（= 现在 + 3000ms）。
- [ ] **AC-3 同房同开局**：两设备用同一 `code` 开局后，双方初始 4×4 棋盘**完全一致**（同 seed + 同 `initGame` 序列）。
- [ ] **AC-4 实时可见**：任一方 `score/steps` 变化后，另一方在 **1.5s 内**经 `state` 轮询可见。
- [ ] **AC-5 满格终局**：一方先合成 2048 → 双方均进入结算卡，胜者正确（`matchResult=1` 或 `2`）。
- [ ] **AC-6 到点判定**：180s 到点比分高者胜；**平分时展示「平局」**（`matchResult=3`），双方结算卡一致。
- [ ] **AC-7 断线重连**：断网 **300s 内**凭 `code+uid` 重连，可恢复对局状态（种子/比分/进度不丢），不重复加人。
- [ ] **AC-8 重连超 TTL**：断网超过 600s 重连失败（房间已 EXPIRE），返回「房间不存在」错误码 3，不报错崩溃。
- [ ] **AC-9 本地不阻塞**：模拟轮询持续超时（≥6s 退避上限）时，本地棋盘照常落子、不卡死，UI 显「同步中…」。
- [ ] **AC-10 结算卡一致**：结算卡复用现有色板 `#edc22e`/`#5b4a1f` 与返回键双形态；「再来一局 / 返回」按钮均可触发。
- [ ] **AC-11 测试回归**：`test/room.test.js` 全过，且既有 167 项 Phase 1 测试不受回归影响。
